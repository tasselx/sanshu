## 4.5 核心：为什么「重连」会被服务端按「新 request」计费（无 resume，是重发 initial request）

这是最反直觉、也是用户最关心的点：**网络层的「重连」≠ 生成层的「恢复」。Cursor 没有「续上同一次 generation」的机制，它做的是「按全新请求的流程，把整个上下文重发一遍」。**

实锤——三次「起一条后端调用」的 span 序列**完全相同**：

| 时刻 | 性质 | span 序列（同一套） |
|---|---|---|
| 08:46:32 | attempt#1（本 turn 首次） | `createControlledExecManager`→`writeInitialRequest`→`handshakeEstablishment`→`rpc.run` |
| **09:04:04** | **attempt#2（断流后的"重连"）** | `createControlledExecManager`→`writeInitialRequest`→`handshakeEstablishment`→`rpc.run` |
| 09:12:12 | 全新 user turn | `createControlledExecManager`→`writeInitialRequest`→`handshakeEstablishment`→`rpc.run` |

- 整份 trace **没有任何 `resume*` / `continueGeneration` 类 span**——不存在「断点续传」。
- 重建那一步带 **`writeInitialRequest`**（行 3345），即「重新写入初始请求体（系统提示 + 完整历史 + 已生成的半截输出）」，和全新请求 08:46:32 / 09:12:12 那两次**用的是同一个动作**。

**机制链（为什么必须这样）：**

1. 一条 request/generation 在服务端 = 一次 `aiserver.v1.ChatService.StreamUnifiedChatWithTools` 双向流 RPC；服务端**按 generation 计费**。
2. 这条流是**有状态、不可断点续传**的：底层 HTTP/2 + TCP 连接一断，承载它的 generation 就死了（`rpc.run error=true`，服务端 tear down）。gRPC/Connect 的 bidi stream 没有「跨新 TCP 连接恢复同一次生成」的协议，模型推理的中间态也没有为任意 resume 做持久化。
3. 要让 turn 续命，客户端只能**新开一条 StreamUnifiedChatWithTools RPC**，用 `writeInitialRequest` 把整轮上下文重发，让模型接着写 → 这是一次**全新 generation** → 服务端再计一行 Included。
4. **为什么 requestId 没变却还多计**：`requestId`（`bf5c618a`）是**客户端的逻辑 turn id**（一次提交一个，跨 attempt 复用）；服务端**按 generation / attempt 计费**。client 视角 = 「1 request、2 attempt」；server 视角 = 「2 generation、2 行账」——两边口径错位，这就是面板多一行的根。
5. **为什么这次"重连"不便宜（219.5万 token）**：因为它不是轻量 socket 重挂，而是 `writeInitialRequest` **重发了整轮已累积 17.5 分钟的上下文** + 继续生成。一次"重连"又烧 200 多万 token，恰好反证它是「全新生成」而非「恢复」。

**一句话**：你看到的是网络层 reconnect（新握手到 `agentn.global.api5.cursor.sh`），但应用/计费层是 **brand-new generation（重发上下文）**。所以「网络波动 → 新 request」成立，且它本质不是 reconnect、而是 re-submit。

## 7. 结论

- **回答「为什么又新开了 request」**：**不是你新开的，也不是计费故障。** 这是**一条** turn（PagePick 会话 `24a56b37` 的 `agent.request bf5c618a`），它的长连接流在 17:04:01 被代理节点 `日本-TY-2` 掐断（此刻 turn 还没跑完），客户端 2 秒后**静默重建**续跑（同一 requestId 的第 2 个 attempt）。服务端把「重建后的 generation」按新 Included request 计费，于是面板出现第 2 行：
  - **04:46 PM / 523.8万** = attempt#1（16:46:32→17:04:01，被掐断）
  - **05:04 PM / 219.5万** = attempt#2（17:04:04 重建后续跑）
- **与上午 12:18 PagePick 那条的关系**：同一个项目（PagePick），但**不同会话**（上午 `a4d63572`，下午 `24a56b37`）。上午那条是「单条长 turn 的用量批次」；下午这条是「长流被掐断→重建多 1 行」。机理同源（都属长流/断流），但下午这次明确有 `error=true` + 同 requestId 二次 attempt，是更标准的「静默分裂」。

## 8. 配置层根因：cursor-direct 覆写从未生效

查 mihomo-party 配置坐实了「为什么走 TY-2」：

| 文件 | 发现 |
|---|---|
| `override/19ebb55f859.js`（cursor-direct） | 写了 `Cursor` 组（默认 **DIRECT**）+ 规则 `DOMAIN-SUFFIX,cursor.sh,Cursor`，日志「执行成功」 |
| `override.yaml` | cursor-direct 标记 **`global: false`**（仅对显式挂载它的 profile 生效） |
| `profile.yaml` | 当前激活 `19af176b759`（shadowsocks-yeli）；**所有 profile 的 `override: []` 全为空** → cursor-direct 谁都没挂 |
| `work/config.yaml`（运行配置） | **无 `Cursor` 组、无 cursor 规则** → 证实覆写没进生效配置 |

结论：cursor-direct 覆写**从未被挂到任何 profile** → `cursor.sh` 落默认 `MATCH` → 全局 `Proxy` 组 → 当前选的 **TY-2**。且其默认值是 `DIRECT`，对「AI 模型区域限制、不能直连」的实际情况也不适用。

## 9. 建议（务实版：此事无法 100% 消除，只能降频）

> 前提澄清：① **不能直连**（provider 区域限制）；② **任何节点都不保证稳定**，长连接被偶发掐断不可根除；③ **重建本身不该消除**（是保命行为，否则 turn 直接死、上下文全丢，比多计一行更亏）。所以目标是「降低发生频率/曝露面」，不是「彻底杜绝」。

1. **别再用被实锤的坏节点 TY-2（净改善，低成本）**：你保证不了任何节点稳定，但 TY-2 有明确偏差证据（6/12 + 6/14 两次掐长连接）。把全局 `Proxy` 组从 TY-2 切到**任意其它节点**即为净改善——「不保证稳定」≠「不比 TY-2 强」。
2. **把超长单 turn 切短（唯一真正可控、最有效的杠杆）**：本次流跑了 **17.5 分钟**才被掐，曝露面巨大。开放式大任务先给分阶段计划、每阶段用 `zhi` 停下确认，把单 turn 压到几分钟，撞上节点抖动的概率断崖下降，同时省钱。
3. **（可选）给 cursor.sh 固定一个 `select` 节点**：避免被全局组自动切换/重均衡在中途掐断。但当前 smart-core 为 `sticky-sessions`，本就倾向保持同节点，此项收益有限；若要做需注意 smart-core 可能改写规则目标，必要时规则直写节点名。
4. **接受残余 +1**：节点抖动时段让 turn 自然收尾再继续；偶发的重建 +1 行属正常代价。
5. **识别口径不变**：面板「同/近时间多行」先按 `requestTraces` 的 `agent.request` span 数 + requestId + `agent.request.attempt` 数 + composerId 核对；**同 requestId 多 attempt = 一条 turn 的流重建（本案）**，不同 requestId/composerId 才是真·多条。
